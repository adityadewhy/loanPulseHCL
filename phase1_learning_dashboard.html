Applied Knowledge & Engineering Intuition

Core Concept
1. Why Asynchronous Python (asyncpg + FastAPI)?

In standard synchronous frameworks (Flask, Django), each request occupies an entire operating system thread. When the thread executes SELECT * FROM loan_applications, it blocks—sitting completely idle while waiting for PostgreSQL across the network socket.

With FastAPI and asyncpg:

  • Single Thread, Thousands of Connections: The asyncio event loop schedules coroutines cooperatively. When your code reaches await db.execute(...), execution yields control back to the event loop.
  • asyncpg Binary Protocol: Unlike psycopg2 (which parses and encodes SQL queries using text representations), asyncpg is written in Cython and uses PostgreSQL's native binary protocol directly, drastically reducing CPU serialization overhead.
Design Pattern
2. FastAPI Dependency Injection & The 'yield' Generator Pattern

Look closely at how database sessions are supplied to route handlers in app/database.py and app/main.py:

async def get_async_db():
    async with AsyncSessionLocal() as session:
        yield session

@app.post("/applications/")
async def create_application(..., db: AsyncSession = Depends(get_async_db)):
    ...

Why is yield used instead of return?

When FastAPI sees a dependency containing yield, it executes the code before the yield prior to calling your route handler. Once the endpoint completes (or even if it raises an HTTP exception), execution resumes after the yield inside the async with block. This guarantees:

  • Automatic session closing and returning connection back to the connection pool.
  • No leaked connections even when unhandled exceptions occur.
  • Complete testability: in tests, you can easily override app.dependency_overrides[get_async_db] with a test database session!
Gotcha Solved
3. The expire_on_commit=False Pitfall in Async SQLAlchemy

In app/database.py, we explicitly pass expire_on_commit=False to sessionmaker:

AsyncSessionLocal = sessionmaker(
    engine, 
    class_=AsyncSession, 
    expire_on_commit=False
)

In synchronous SQLAlchemy, after you run await db.commit(), SQLAlchemy automatically marks all object attributes as expired. If your endpoint returns return db_loan, FastAPI's response serializer attempts to read db_loan.id and db_loan.status.

In sync SQLAlchemy, this triggers a transparent "lazy load" query. But in async SQLAlchemy, lazy loading without await is strictly forbidden and causes a fatal crash: MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here. Setting expire_on_commit=False ensures the committed object attributes stay loaded in memory, allowing FastAPI to serialize them cleanly without extra queries.

Production Principle
4. Why Alembic Migrations instead of Base.metadata.create_all?

Many beginner tutorials use await conn.run_sync(Base.metadata.create_all) in a startup event. Here is why that fails in production:

  • Schema Evolution: create_all only creates tables that do not exist. It cannot add new columns, alter types, create foreign keys, or rename fields on existing tables.
  • Distributed Conflicts: In a production Kubernetes cluster with 4 replicas of your API, all 4 instances would compete to run create_all on startup, risking database locking issues.
  • Auditable Versioning: Alembic creates a dedicated table in PostgreSQL: alembic_version containing the current migration hash (e.g. c47c7f042184). You can deploy migrations as an isolated pre-deployment job in CI/CD before any application container starts up.
Architecture
